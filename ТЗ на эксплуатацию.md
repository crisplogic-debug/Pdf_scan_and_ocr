## 1. Назначение и цели

Программа предназначена для:
- **сбора** исходных данных о техническом состоянии парка авиационной техники (АТ)
  из Excel-файлов с произвольной структурой граф;
- **хранения** этих данных с полной **историей изменений** параметров каждого
  воздушного судна (ВС);
- **прогнозирования** отхода ВС в ремонт и вывода из эксплуатации на горизонте
  планирования (период ГПВ — государственной программы вооружения — и общий период
  прогноза);
- **планирования** закупок и поставок в ремонт по модификациям/конкретным ВС;
- формирования **отчётов** по результатам анализа.

Целевой пользователь — аналитик/инженер, ведущий пономерной учёт парка и
формирующий прогноз потребности в ремонте и обновлении парка.

## 2. Глоссарий и термины

| Термин | Расшифровка | Единицы / тип |
|---|---|---|
| **ВС** | Воздушное судно (конкретный образец) | — |
| **Тип техники** | Верхний уровень иерархии (напр. «Ил-76») | строка-справочник |
| **Модификация** | Подтип (напр. «Ил-76МД») | строка-справочник, привязана к типу |
| **Заводской (серийный) номер** | Уникальный неизменяемый идентификатор ВС | строка |
| **Бортовой номер** | Регистрационный/бортовой номер (может меняться) | строка |
| **База приписки** | Подразделение приписки (может меняться) | строка |
| **СС (срок службы)** | Календарный срок службы | **годы и месяцы** (точность — месяц, накапливается помесячно) |
| **Ресурс** | Наработка | **часы налёта (л.ч.)** |
| **МРСС** | Межремонтный срок службы (СС между ремонтами) | **годы/месяцы** |
| **МРР** | Межремонтный ресурс (наработка между ремонтами) | **часы налёта** |
| **Назначенный СС** | Полный (предельный) срок службы до списания | **годы/месяцы** (число месяцев от даты выпуска) |
| **Назначенный ресурс** | Полный (предельный) ресурс до списания | **часы налёта** |
| **Остаток СС / ресурса** | Остаток до ближайшего предела | месяцы / часы налёта |
| **Дата крайнего ремонта** | Дата последнего выполненного ремонта | дата |
| **Дата актуализации** | Дата, на которую достоверны данные параметра | дата |
| **ГПВ** | Государственная программа вооружения (период планирования) | диапазон лет |
| **Отход в ремонт** | Событие постановки ВС в ремонт | год прогноза |

## 6. Структура базы данных

Ключевой принцип (требование ТЗ): **идентификационные данные ВС статичны, все
эксплуатационные параметры историзируются** с привязкой к дате актуализации и
источнику получения (парсинг/ручной ввод).

### 6.1. Справочники

```sql
-- Тип техники (0-й уровень дерева), напр. "Ил-76"
CREATE TABLE equipment_type (
    id            INTEGER PRIMARY KEY,
    name          TEXT NOT NULL UNIQUE,
    repair_duration_years REAL NOT NULL DEFAULT 1, -- продолжительность ремонта для типа
    comment       TEXT
);

-- Модификация (1-й уровень), напр. "Ил-76МД"
CREATE TABLE modification (
    id            INTEGER PRIMARY KEY,
    type_id       INTEGER REFERENCES equipment_type(id) ON DELETE SET NULL,
    name          TEXT NOT NULL UNIQUE,
    comment       TEXT
);
```

### 6.2. Идентификация ВС (статика)

```sql
-- Конкретный образец (2-й уровень). Идентификатор — factory_number.
CREATE TABLE aircraft (
    id              INTEGER PRIMARY KEY,
    factory_number  TEXT NOT NULL UNIQUE,   -- НЕИЗМЕНЯЕМЫЙ идентификатор
    modification_id INTEGER REFERENCES modification(id),
    release_date    DATE,                   -- дата выпуска (статична)
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    is_engine       INTEGER DEFAULT 0       -- задел под учёт двигателей (см. п.12.5)
);
```

> Замечание по несвязке: ТЗ называет идентификатором тройку
> «база + модификация + заводской номер», но одновременно указывает, что база и
> бортовой номер меняются. См. п.12.1 — предлагается идентифицировать ВС
> **только по заводскому номеру**, а базу/модификацию вести в истории.

### 6.3. Историзация параметров (ядро модели)

Предлагается **temporal EAV** (entity-attribute-value с датами) — гибко при
изменяемом наборе граф Excel и удобно для «истории по каждому параметру».

```sql
-- Справочник параметров (расширяемый без изменения схемы)
CREATE TABLE param_def (
    code        TEXT PRIMARY KEY,  -- 'base','tail_number','mrss','mrr',
                                   -- 'remain_ss','remain_res','last_repair_date',
                                   -- 'assigned_ss','assigned_res', ...
    title       TEXT NOT NULL,     -- отображаемое название
    value_type  TEXT NOT NULL,     -- 'text' | 'number' | 'date'
    unit        TEXT               -- 'лет','ч','пос.' и т.п.
);

-- История значений параметров ВС
CREATE TABLE aircraft_param_history (
    id            INTEGER PRIMARY KEY,
    aircraft_id   INTEGER NOT NULL REFERENCES aircraft(id) ON DELETE CASCADE,
    param_code    TEXT NOT NULL REFERENCES param_def(code),
    value_text    TEXT,            -- заполняется по value_type
    value_num     REAL,
    value_date    DATE,
    actual_on     DATE NOT NULL,   -- дата актуализации (на какую дату достоверно)
    source        TEXT NOT NULL,   -- 'import' | 'manual'
    import_batch_id INTEGER REFERENCES import_batch(id),
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX ix_aph_lookup ON aircraft_param_history(aircraft_id, param_code, actual_on);
```

Текущее значение параметра = запись с максимальным `actual_on` (а при равенстве —
с максимальным `created_at`). История параметра для редактора = все записи по
`aircraft_id + param_code`, отсортированные по `actual_on`.

> Альтернатива (широкая «снимочная» таблица) рассмотрена в п.12.2.

### 6.4. Импорт (журнал)

```sql
CREATE TABLE import_batch (
    id            INTEGER PRIMARY KEY,
    file_name     TEXT,
    actual_on     DATE NOT NULL,        -- дата, на которую актуальны данные (выбор пользователя)
    imported_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    rows_total    INTEGER,
    rows_new_ac   INTEGER,              -- сколько новых ВС создано
    mapping_json  TEXT                  -- использованное сопоставление граф
);
```

### 6.5. Плановые работы (модуль 3.2)

```sql
-- Планы привязаны к конкретному ВС, актуальность — по модификации (см. п.12.4)
CREATE TABLE planned_work (
    id            INTEGER PRIMARY KEY,
    aircraft_id   INTEGER REFERENCES aircraft(id) ON DELETE CASCADE,
    kind          TEXT NOT NULL,        -- 'purchase' | 'repair'
    planned_date  DATE NOT NULL,
    cost          REAL,
    comment       TEXT
);

-- Дата актуальности плана по модификации
CREATE TABLE plan_actuality (
    modification_id INTEGER PRIMARY KEY REFERENCES modification(id),
    actual_on       DATE NOT NULL
);
```

## 7. Парсинг Excel

### 7.1. Мастер импорта (ImportWizard), шаги:

1. **Выбор файла** (`.xlsx`/`.xls`), выбор листа.
2. **Предпросмотр**: панель-таблица первых N строк (напр. 50) с буквами столбцов
   (A, B, C…) в заголовке — чтобы видеть, в какой графе какие данные.
3. **Сопоставление граф ↔ параметров ВС**: для каждого параметра
   (`base, modification, release_date, tail_number, factory_number, mrss, mrr,
   remain_ss, remain_res, last_repair_date, assigned_ss, assigned_res`)
   — выпадающий список столбцов. Значения по умолчанию берутся из
   `config.import.last_column_mapping`. **Автосохранение** выбора по завершении.
4. **Выбор даты актуализации** данных по календарю (`QDateEdit`/`QCalendarWidget`).
5. **Запуск парсинга** и **отчёт о результатах**.

### 7.2. Логика разбора строк

- Строка модификации — это строка, где заполнено поле `modification`/идентифицирующие
  поля ВС. **Пустые строки под модификацией = двигатели** → пока **пропускаются**
  (но фиксируются в отчёте импорта; задел `aircraft.is_engine` — п.12.5).
- Для каждой валидной строки:
  1. По `factory_number` ищем ВС в БД.
  2. Если нет — создаём `aircraft` (factory_number, modification, release_date),
     помечаем как **новый**.
  3. Все эксплуатационные параметры пишем в `aircraft_param_history` с
     `actual_on = выбранная дата`, `source='import'`, `import_batch_id`.
- Если модификации нет в справочнике — предложить создать (или авто-создать
  с привязкой к типу по правилу из п.12.3).

### 7.3. Отчёт о результатах импорта

Диалог/панель с итогами:
- всего строк обработано, пропущено (двигатели/пустые), ошибок;
- список **новых ВС** с основной информацией (база, модификация, зав.№, борт.№,
  остатки СС/ресурса, дата крайнего ремонта);
- список изменённых параметров (опционально).

## 8. Модуль «Главное окно»

Меню:
- **Файл** → `Настройки`, `Выход`
- **Отчёты** → (список отчётов)

Содержимое (компоновка сверху вниз):
- Панель управления: кнопки запуска модулей «Пономерной учёт ВС», «Плановые работы»;
  поля выбора периодов прогноза — **текущий год**, **период ГПВ** (от/до),
  **общий период прогноза** (от/до) — сохраняются в `config.forecast`.
- **Дашборд текущего состояния парка** (см. §8.4) — занимает основную область окна.

При старте Программы (п.0 ТЗ):
- читается `config.json` → путь к БД;
- если БД не задана/не найдена — диалог: **создать новую** (выбор пути) или
  **подключиться к существующей** (выбор файла);
- при создании — инициализация схемы и справочника параметров `param_def`;
- после загрузки данных автоматически строится дашборд (§8.4).

### 8.4. Дашборд текущего состояния (количественный, в диаграммах)

Сводная визуальная панель по **текущему состоянию всех модификаций** на крайнюю
дату актуализации. Реализуется на `PySide6.QtCharts`. Все диаграммы — кликабельны
(переход в «Пономерной учёт» с фильтром по выбранной модификации/состоянию).

**Верхняя строка — KPI-плитки (крупные числа):**
- всего ВС в парке; число модификаций/типов;
- ВС в эксплуатации; ВС в ремонте (по плану текущего года);
- ВС, выводимых из эксплуатации в текущем/следующем году;
- средний остаток СС по парку (%), средний остаток ресурса (%).

**Диаграммы:**
1. **Количество ВС по модификациям** — горизонтальная столбчатая диаграмма
   (`QBarSeries`), сортировка по убыванию.
2. **Структура парка по типам** — круговая диаграмма (`QPieSeries`), доля каждого типа.
3. **Распределение по остатку СС** — столбчатая диаграмма по корзинам остатка
   СС (0–20 %, 20–40 %, …, 80–100 %); цвет — от красного к зелёному.
4. **Распределение по остатку ресурса** — аналогично по часам налёта.
5. **Прогноз потребности в ремонте по годам** — накопительная столбчатая
   диаграмма (`QStackedBarSeries`) с разбивкой по модификациям, по общему периоду
   прогноза; поверх — линия плановых поставок в ремонт (из модуля 3.2).
6. **Прогноз вывода из эксплуатации по годам** — столбчатая диаграмма.
7. **«Светофор» состояния** — сводная таблица/heat-map по модификациям:
   столбцы (всего, в строю, в ремонте, средний остаток СС %, средний остаток
   ресурса %), фон ячеек остатков — красно-зелёный градиент (как заливка дерева).

**Управление:** селектор периода (текущий год / период ГПВ / общий период);
фильтр по типу/модификации; кнопка **«Экспорт дашборда»** (§8.5).

Срез данных для дашборда инкапсулируется в `DashboardService` (агрегаты считаются
SQL-запросами по `aircraft` + последним записям `aircraft_param_history`,
прогнозные числа — через `ForecastService`).

### 8.5. Отчёты и вывод данных (наглядное представление)

Пункт меню **«Отчёты»** (доступен в Главном окне и в окне пономерного учёта).
Общий движок отчётов `ReportService`. Каждый отчёт можно **просмотреть** (диалог
предпросмотра с таблицей и диаграммами), **экспортировать в Excel** (`openpyxl`,
с форматированием и цветовой заливкой), **в PDF/на печать** (`QPrinter`/`QPdfWriter`).

Состав отчётов:
1. **Состояние парка по модификациям** — таблица: модификация, тип, кол-во ВС,
   средние остатки СС/ресурса (% и абсолют), число в ремонте, к выводу; с
   цветовой заливкой остатков. Дублируется ключевыми диаграммами дашборда.
2. **Пономерная ведомость** — по каждому ВС: база, борт.№, зав.№, дата выпуска,
   МРСС, МРР, остатки СС/ресурса, дата крайнего ремонта, назначенные СС/ресурс,
   расчётные годы отхода в ремонт и вывода из эксплуатации, дата актуализации,
   источник данных.
3. **План-прогноз потребности в ремонте** — матрица «модификация × годы» с числом
   ВС в ремонт по годам (прогноз) и отдельной строкой «План поставок»; итоги по годам.
4. **План вывода из эксплуатации** — матрица «модификация × годы».
5. **Плановые закупки и поставки в ремонт (финансовый)** — по модификациям/ВС:
   даты и стоимости, итоги по годам и по модификациям.
6. **История изменения параметров ВС** — выгрузка истории выбранного ВС/модификации.
7. **Экспорт дашборда** — снимок диаграмм + сводная таблица «светофора» в PDF.

Принципы наглядности (сквозные для всех представлений):
- единая цветовая семантика остатков: **красный → жёлтый → зелёный** (мало → много);
- проценты дублируются абсолютными значениями (месяцы СС, часы налёта);
- даты — в формате `ММ.ГГГГ`/`ДД.ММ.ГГГГ`; периоды прогноза — по годам;
- в таблицах — заморозка заголовков, сортировка, ширины колонок из `config`.

Состав/набор колонок отчётов настраивается; параметры последнего экспорта
(каталог, формат) сохраняются в `config`.

## 9. Модуль «Пономерной учёт ВС»

Меню окна:
- **Загрузка данных** (запуск ImportWizard)
- **Справочник типов** (TypeCatalogDialog)
- **Отчёты**

### 9.1. Слева — дерево техники

Три уровня:
- **0 уровень** (опционально) — **тип техники** (Ил-76). Состав типа
  (какие модификации входят) редактируется в отдельном окне «Справочник типов»
  (добавить/изменить/удалить модификации из типа).
- **1 уровень** — **модификации** (Ил-76М, Ил-76МД).
- **2 уровень** — **конкретные образцы** (база приписки + бортовой номер).

**Заливка строк (две полосы-индикатора как фон строки):**
- **Полоса 1 (светло-красная)** — % остатка **срока службы**:
  `остаток_СС / МРСС`, где остаток считается между датой крайнего ремонта
  (если есть), текущей датой и МРСС.
- **Полоса 2 (светло-зелёная)** — % остатка **ресурса**:
  `остаток_ресурса / МРР`.
- Для **уровня 2** — по данным конкретного ВС на крайнюю дату актуализации.
- Для **уровня 1** — агрегат по всем входящим образцам (метод агрегации — п.12.9,
  по умолчанию **среднее**).

> Реализация: делегат `QStyledItemDelegate`, рисующий две горизонтальные полосы
> заданной ширины (в %) на фоне ячейки названия.

### 9.2. Справа — панель информации

#### 9.2.1. Таблица прогноза отхода (тип «Гант»)
- Колонки — годы общего периода прогноза / периода ГПВ (переключение).
- Для **уровня 2** — диаграмма по одному ВС: расход СС, год(ы) отхода в ремонт,
  выход из эксплуатации при достижении назначенного СС. **Только по датам СС**
  (без ресурсных показателей).
- Для **уровня 1** — аналогично по всем входящим ВС; внизу строка
  **«Потребность в ремонте»** (число ВС, уходящих в ремонт в данном году).
- Продолжительность ремонта — из настроек типа (`repair_duration_years`, обычно 1).
- СС ВС в ремонте **не расходуется**; продолжительность ремонта **прибавляется**
  к назначенному СС (сдвигает дату вывода из эксплуатации). Подробно — п.11.

#### 9.2.2. Данные по ВС (только для уровня 2)
Редактируемая панель всех параметров выбранного ВС:
- Поле **даты** — текстовое поле + кнопка календаря.
- У каждого поля — **мелким шрифтом/цветом** метка источника
  (`автоматически (парсинг)` / `ввод вручную`).
- Для каждого параметра — **список истории** (значение ↔ дата актуализации):
  пользователь может **удалять**, **изменять** записи и **добавлять новые за
  прошлый период**.
- Рекомендуемая реализация наглядности (см. также п.12.10):
  - компактный виджет на параметр: текущее значение сверху + раскрывающийся
    список (`disclosure`) с историей в виде мини-таблицы (значение | дата | источник);
  - редактирование инлайн; добавление новой записи — строка «+».

## 10. Модуль «Плановые работы»

- Набор параметров **по модификациям ВС**, ведётся **по каждому ВС отдельно**:
  - **планируемая закупка**: дата, стоимость;
  - **планируемая поставка в ремонт**: дата, стоимость.
- **Дата актуальности** ведётся **по каждой модификации** (`plan_actuality`).
- Запланированные поставки в ремонт **автоматически отражаются** в таблице
  прогноза модуля пономерного учёта **отдельной строкой** — суммарное количество
  ВС в ремонт по годам (см. соотношение «план vs прогноз» в п.12.4).

## 11. Алгоритмы прогнозирования

> **Единицы и точность:** срок службы измеряется в **месяцах** (год+месяц,
> накапливается помесячно); ресурс — в **часах налёта**. Все расчёты по СС ведутся
> в месяцах с точностью до месяца, а в таблице-Ганте агрегируются **по годам**.

### 11.1. Исходные данные по ВС (на крайнюю дату актуализации)
- `last_repair_date` (если нет — точка отсчёта = `release_date`);
- `mrss_months` — межремонтный СС в месяцах;
- `assigned_ss_months` — назначенный СС в месяцах от даты выпуска (см. п.12.6);
- `repair_duration_months` — продолжительность ремонта из настроек типа
  (хранится в годах, переводится в месяцы; по умолчанию 12).

### 11.2. Модель ремонтных циклов (по календарю/СС, шаг — месяц)
Алгоритм для одного ВС (псевдокод; все величины — в месяцах):

```
start = last_repair_date or release_date
assigned_end = add_months(release_date, assigned_ss_months)   # предельная дата (до сдвигов)
cursor = start
while cursor < assigned_end:
    next_repair = add_months(cursor, mrss_months)             # очередной выход в ремонт
    if next_repair >= assigned_end:
        событие: ВЫВОД_ИЗ_ЭКСПЛУАТАЦИИ в год(assigned_end)
        break
    событие: ОТХОД_В_РЕМОНТ в год(next_repair)
    # во время ремонта СС не расходуется → сдвигаем предел вправо на длительность ремонта
    assigned_end = add_months(assigned_end, repair_duration_months)
    cursor = add_months(next_repair, repair_duration_months)  # ВС выходит из ремонта
```

- В каждом году периода прогноза для ВС фиксируется статус: «эксплуатация»,
  «в ремонте», «отход в ремонт», «вывод из эксплуатации».
- **Потребность в ремонте по году** (для уровня 1) = число ВС с событием
  ОТХОД_В_РЕМОНТ в этом году.

> Роль ресурса (МРР/остаток ресурса) в данном прогнозе — **только индикаторная
> заливка** (п.9.1). Влияние интенсивности эксплуатации на прогноз отхода —
> опциональное расширение, см. п.12.6.

### 11.3. Учёт плановых поставок в ремонт
- Если для ВС есть `planned_work(kind='repair')`, он **переопределяет**
  расчётный год отхода (план приоритетнее прогноза) — либо отображается отдельной
  строкой «план», см. п.12.4.

## 12. Выявленные несвязки и принятые решения

> **Статус:** все пункты согласованы Заказчиком (27.06.2026). Принят **Вариант А**
> по всем пунктам. Ниже сохранены альтернативы для истории решений.

### 12.1. Идентификатор ВС — ✅ Вариант А (принято)
Несвязка: идентификатором назван «база + модификация + зав.№», но база и
модификация по тексту ТЗ изменяемы.
- ✅ **А (принято):** идентификатор — **только заводской номер**; база, модификация,
  бортовой номер — в истории параметров.
- Б: идентификатор — зав.№ + модификация (модификация неизменяема, смена = новый ВС).
- В: как в ТЗ (тройка) — но тогда смена базы порождает «нового» ВС (не рекомендуется).

### 12.2. Модель хранения истории — ✅ Вариант А (принято)
- ✅ **А (принято):** temporal EAV (п.6.3) — гибко при изменчивом наборе граф Excel.
- Б: широкая таблица-снимок `aircraft_snapshot(actual_on, …все поля…)` — проще
  читается, но жёсткая схема и дублирование при изменении одного параметра.

### 12.3. Привязка модификации к типу при импорте — ✅ Вариант А (принято)
- ✅ **А (принято):** новые модификации создаются «без типа», пользователь привязывает
  их к типу в «Справочнике типов» (в дереве показываются в узле «Без типа»).
- Б: тип определяется автоматически по префиксу имени модификации (правило regex).

### 12.4. Соотношение «план поставки в ремонт» vs «прогноз потребности» — ✅ Вариант А (принято)
- ✅ **А (принято):** две раздельные строки — «Потребность (прогноз)» и
  «План (поставки)»; расхождение подсвечивается.
- Б: план **замещает** прогноз для тех ВС, где он задан (одна строка-факт).

### 12.5. Учёт двигателей — ✅ Вариант А (принято)
- ✅ **А (принято):** строки двигателей пропускаются при импорте, но в схеме есть
  задел (`aircraft.is_engine`, связь «планер ↔ двигатели») для будущего этапа.
- Б: полностью игнорировать (без задела).

### 12.6. Единицы измерения и роль ресурса; назначенный СС — ✅ согласовано
- ✅ **Ресурс (МРР/остаток/назначенный)** — в **часах налёта (л.ч.)**.
- ✅ **Срок службы** — в **годах и месяцах**, точность — **месяц** (накапливается
  помесячно). Хранится как число месяцев от даты выпуска.
- ✅ **Назначенный СС** — число месяцев от даты выпуска (Вариант А).
- ✅ Влияние интенсивности эксплуатации (история ресурса) на прогноз отхода — на
  текущем этапе **не влияет** (прогноз только по СС); история ресурса собирается
  для будущего моделирования (расширение — расчёт средней интенсивности
  Δл.ч./Δмесяц и отход по наступлению любого предела).

### 12.7. Поддержка форматов Excel — ✅ Вариант А (принято)
- ✅ **А (принято):** поддержать `.xlsx` (openpyxl) и `.xls` (xlrd/pyexcel).
- Б: только `.xlsx`.

### 12.8. Слой доступа к данным — ✅ Вариант А (принято)
- ✅ **А (принято):** «голый» `sqlite3` + тонкие репозитории (меньше зависимостей в EXE).
- Б: SQLAlchemy (удобнее миграции/модели, но больше размер EXE).

### 12.9. Метод агрегации заливки на уровне 1 (модификация) — ✅ Вариант А (принято)
- ✅ **А (принято):** **среднее** по входящим ВС (для заливки дерева и для
  агрегатов дашборда).
- Б: **минимум** остатка (наихудший образец) — консервативная оценка.
- В: показывать обе полосы как диапазон min–avg.

### 12.10. Реализация редактора истории параметра — ✅ Вариант А (принято)
- ✅ **А (принято):** на каждый параметр — поле «текущее значение» + раскрывающийся

- Б: одна общая таблица-история всех параметров ВС (вкладка «История»).

### 12.11. Хранение геометрии окон/ширин колонок — ✅ Вариант А (принято)

- Б: через `QSettings` (реестр Windows) — но это противоречит «настройки в json».

## 13. Нефункциональные требования

- **ОС:** Windows 10 и выше, x64.
- **Поставка:** один `.exe` (PyInstaller `--onefile`) со всеми зависимостями;
  `config.json` и (опционально) пустая БД создаются при первом запуске.

- **Надёжность:** импорт в одной транзакции; при ошибке — откат батча.
- **Локализация:** интерфейс на русском языке.
- **Логирование:** файл лога рядом с EXE (ротация).
- **Темы оформления:** светлая/тёмная (qss), выбор в настройках.
- **Автосохранение** геометрии окон и ширин колонок (debounce).
