## 1. Назначение и цели проекта

### 1.1. Назначение

Разработать настольное GUI-приложение для автоматизированной обработки отсканированных PDF-документов: постраничное распознавание текста с помощью LLM OCR, формирование поисковых PDF/A с автоматическим извлечением номера и наименования документа, векторизация содержимого для RAG-базы и семантический поиск по документам в табличном виде (без LLM-агента).

### 1.2. Цели

1. Преобразование сканированных PDF в **PDF/A** с **встроенным текстовым слоем** (полнотекстовый поиск в PDF-ридере).
2. Сохранение полного распознанного текста в **Markdown** для последующей обработки и RAG.
3. Построение **векторной базы знаний** (RAG) на основе содержимого документов.
4. Предоставление **поискового модуля** для семантического поиска: один запрос — одна таблица результатов с номером документа, наименованием, краткой вырезкой текста и ссылкой на PDF/A.
5. **Подтверждение пользователем** автоматически извлечённых номера и наименования документа после обработки (подтвердить как есть или отредактировать и подтвердить).
6. Модульное разделение функций: обработка, управление RAG, поиск.
7. Работа с LLM-моделями (OCR, embedding) на **том же ПК**, что и приложение, или на **отдельном ПК в LAN** (доступ по `localhost` / IP и порту); **ручной** запуск и остановка серверов моделей; **одновременно активна только одна модель**.
8. **Поэтапная обработка** в модуле 1: сначала OCR (распознанные документы → каталог ожидания векторизации), затем embedding (поочерёдная векторизация → каталог готовых документов).

### 1.3. Целевая аудитория

Пользователи, работающие с архивами отсканированных документов (делопроизводство, юридические отделы, библиотеки, личные архивы), которым необходимы структурированный поиск по содержимому, контроль метаданных документов (номер, наименование) и быстрый доступ к исходным PDF/A.

## 2. Общая архитектура

### 2.1. Принципы архитектуры

| Принцип | Описание |
|---------|----------|
| **Модульность** | Три независимых функциональных модуля с общим ядром (core) |
| **Слабая связанность** | Модули взаимодействуют через общие сервисы, конфигурацию и файловую структуру |
| **Расширяемость** | Возможность добавления новых моделей, провайдеров API, форматов экспорта |

## 3. LLM-сервисы (локальный ПК и LAN API)

Модели OCR и embedding могут развёртываться **на том же компьютере**, где работает приложение (`127.0.0.1` / `localhost`), либо на **отдельном ПК в локальной сети**. В обоих случаях приложение подключается по HTTP API: `http://<host>:<port>`.

**Критическое ограничение:** в один момент времени на целевом GPU/ПК должна работать **только одна** модель. Приложение **не запускает OCR и embedding одновременно** — пользователь вручную переключает активный сервер.

### 3.1. OCR — Qwen3-VL-30B-A3B-Instruct

- **Модель:** [Qwen/Qwen3-VL-30B-A3B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct)
- **Назначение:** Постраничное распознавание текста, определение структуры (заголовки, содержание, таблицы).
- **Развёртывание:** Локальный ПК пользователя **или** отдельный ПК в LAN; `host` по умолчанию для локального режима — `127.0.0.1`.
- **Ожидаемый интерфейс API** (адаптер в приложении должен поддерживать OpenAI-compatible и кастомный эндпоинт):

| Параметр | Описание |
|----------|----------|
| `base_url` | Базовый URL сервиса |
| `endpoint` | `/v1/chat/completions` или кастомный `/ocr/recognize` |
| `timeout_sec` | Таймаут запроса (по умолчанию 120 с на страницу) |
| `max_retries` | Число повторов при сетевой ошибке |
| `image_format` | PNG/JPEG, DPI рендера страницы |
| `prompt_template` | Настраиваемый промпт для OCR |

**Входные данные на страницу:** изображение страницы (base64 или multipart), номер страницы, язык (опционально).

**Выходные данные:** распознанный текст (plain/markdown), метаданные структуры (заголовки H1–H3, блок «Содержание»), уровень уверенности (если API отдаёт).

### 3.2. Embedding — Qwen3-Embedding-8B

- **Модель:** [Qwen/Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B)
- **Назначение:** Векторизация чанков текста для RAG.
- **Развёртывание:** Локальный ПК пользователя **или** отдельный ПК в LAN; `host` по умолчанию — `127.0.0.1`.

| Параметр | Описание |
|----------|----------|
| `base_url` | Базовый URL |
| `endpoint` | `/v1/embeddings` или `/embed` |
| `batch_size` | Размер пакета чанков (1–64) |
| `dimensions` | Размерность вектора (если модель поддерживает truncate) |
| `normalize` | L2-нормализация векторов |

### 3.3. Использование Embedding в поисковом модуле

Модуль 3 **не использует LLM-агента**. Для семантического поиска применяется только модель **Qwen3-Embedding-8B** (тот же сервис, что и при индексации в модулях 1 и 2):

- **Векторизация запроса:** пользовательский текст → embedding через HTTP API (тот же сервер, что при индексации).
- **Поиск:** `vectorstore.search()` по коллекции документов с сортировкой по релевантности (косинусная близость).
- **Формирование результата:** для каждого найденного чанка извлекаются метаданные документа и текстовая вырезка; LLM для генерации ответов **не вызывается**.

| Параметр | Описание |
|----------|----------|
| `base_url`, `endpoint` | Те же, что для embedding при индексации |
| `normalize` | L2-нормализация вектора запроса (согласованно с индексацией) |
| `timeout_sec` | Таймаут запроса embedding (по умолчанию 30 с) |

### 3.4. Ручное управление серверами моделей

Запуск и остановка серверов OCR и embedding выполняются **вручную** пользователем из GUI (аналогично запуску локального сервера разработки). Автоматический старт моделей при запуске приложения **не предусмотрен**.

#### 3.4.1. Общие правила

| Правило | Описание |
|---------|----------|
| **Один активный сервер** | Одновременно может быть запущен **только OCR или только embedding**. Запуск второго сервера при работающем первом **блокируется** с уведомлением: «Остановите сервер OCR перед запуском embedding» (и наоборот). |
| **Ручной режим** | Кнопки «Запустить сервер» / «Остановить сервер» для каждой модели; обработка очереди возможна только при запущенном соответствующем сервере. |
| **Локальный и удалённый режим** | Если модель на другом ПК — кнопки запуска/остановки скрыты или неактивны; остаётся только проверка подключения (health-check). Управление сервером — на стороне администратора удалённого хоста. |
| **Переключение этапов** | Переход от этапа 1 (OCR) к этапу 2 (embedding): пользователь останавливает OCR-сервер → запускает embedding-сервер → запускает векторизацию очереди. |

#### 3.4.2. Настройки сервера модели (локальный режим)

| Параметр | Описание |
|----------|----------|
| `model_server.mode` | `local` — управление из приложения; `remote` — только подключение к уже запущенному API |
| `model_server.ocr.command` | Команда запуска OCR-сервера (bat/ps1/python), например: `python -m vllm.entrypoints...` |
| `model_server.ocr.workdir` | Рабочий каталог процесса |
| `model_server.ocr.port` | Порт HTTP API (default 8000) |
| `model_server.embed.command` | Команда запуска embedding-сервера |
| `model_server.embed.workdir` | Рабочий каталог процесса |
| `model_server.embed.port` | Порт HTTP API (default 8001) |
| `model_server.startup_timeout_sec` | Ожидание готовности API после старта (default 120) |
| `model_server.graceful_stop_sec` | Таймаут корректной остановки процесса (default 30) |

#### 3.4.3. Состояния сервера в UI

| Состояние | Визуализация | Доступные действия |
|-----------|--------------|-------------------|
| **Остановлен** | Серый | «Запустить сервер» (если другой сервер не активен) |
| **Запускается** | Жёлтый, анимация | «Отмена» (опционально) |
| **Работает** | Зелёный | «Остановить сервер», обработка очереди этапа |
| **Ошибка** | Красный | «Повторить запуск», просмотр лога процесса |
| **Удалённый хост** | Синий / по health-check | Только «Проверить подключение» |

Приложение отслеживает PID дочернего процесса (локальный режим) и при «Остановить сервер» завершает процесс; при аварийном завершении — обновляет индикатор и блокирует очередь.

### 3.5. Индикатор подключения к API

Для каждого сервиса (OCR, Embedding) в GUI отображается:

| Состояние | Визуализация | Поведение |
|-----------|--------------|-----------|
| **Подключено** | Зелёный индикатор | Успешный health-check / тестовый запрос < 5 с назад |
| **Проверка** | Жёлтый, анимация | Идёт ping или запрос |
| **Отключено** | Красный | Ошибка сети, таймаут, HTTP 4xx/5xx |
| **Не настроено** | Серый | host/порт не заданы или сервер остановлен |

Периодическая проверка: каждые **30 с** (настраиваемо). Ручная кнопка «Проверить подключение» на панели каждого модуля.

## 4. Файловая структура данных

### 4.1. Каталоги модуля обработки PDF (настраиваемые пути)

Обработка разделена на **два этапа** с разными каталогами:

```
<корень_данных>/
├── inbox/                         # Этап 1: входящие сканы (пользователь кладёт PDF)
├── processing/                    # Этап 1: файлы в процессе OCR
├── pending_vectorization/         # Этап 1 завершён: распознанные, ожидают embedding
│   └── <имя_документа>/
│       ├── source.pdf
│       ├── document.pdf           # PDF/A с текстовым слоем
│       ├── document.md
│       ├── metadata.json          # metadata_confirmed, processing_stage: "ocr_done"
│       └── pages/
└── documents/                     # Этап 2 завершён: готовые к поиску
    └── <имя_документа>/
        ├── source.pdf
        ├── document.pdf
        ├── document.md
        ├── metadata.json          # processing_stage: "ready", vectorized: true
        └── pages/
```

| Каталог | Этап | Содержимое |
|---------|------|------------|
| `inbox/` | 1 | Исходные PDF, ожидающие OCR |
| `processing/` | 1 | PDF в процессе распознавания |
| `pending_vectorization/` | 1→2 | OCR завершён, метаданные подтверждены, **векторизация не выполнена** |
| `documents/` | 2 | OCR + embedding завершены, документ доступен в поиске |

### 4.2. Векторная база данных

```
<корень_данных>/vectorstore/
├── chroma/                   # или qdrant_local/
├── collections/
│   └── documents/            # Коллекция по умолчанию
└── registry.json             # Реестр: document_id ↔ путь ↔ chunk_ids
```

### 4.3. Метаданные документа (обязательные поля)

Поля `document_number` и `document_name` извлекаются **автоматически** при обработке PDF (модуль 1) и подлежат **подтверждению пользователем** перед окончательной индексацией в RAG (см. разделы 5 и 6).

```json
{
  "document_id": "uuid",
  "document_number": "12/34-2024",
  "document_name": "Договор поставки оборудования",
  "document_number_source": "auto",
  "document_name_source": "auto",
  "metadata_confirmed": false,
  "metadata_confirmed_at": null,
  "processing_stage": "ocr_done",
  "vectorized": false,
  "file_path": "C:/.../pending_vectorization/Договор_2024/document.pdf",
  "md_path": "C:/.../documents/Договор_2024/document.md",
  "created_at": "2026-06-16T12:00:00",
  "ocr_model": "Qwen3-VL-30B-A3B-Instruct",
  "embedding_model": "Qwen3-Embedding-8B",
  "pages_count": 24
}
```

| Поле | Описание |
|------|----------|
| `document_number` | Регистрационный/внутренний номер документа (извлекается из текста первых страниц, штампа, реквизитов) |
| `document_name` | Наименование/заголовок документа (извлекается из заголовка, темы письма, названия в тексте) |
| `document_number_source` / `document_name_source` | `auto` — сформировано автоматикой; `user` — скорректировано пользователем |
| `metadata_confirmed` | `false` — ожидает подтверждения; `true` — пользователь подтвердил номер и наименование |
| `metadata_confirmed_at` | Дата и время подтверждения (ISO 8601) |
| `processing_stage` | `ocr_done` — в `pending_vectorization`; `ready` — в `documents/` |
| `vectorized` | `false` — ожидает embedding; `true` — чанки записаны в vectorstore |

Документы в `pending_vectorization/` с `metadata_confirmed: true` **не участвуют** в поиске до завершения этапа 2. Документы с `metadata_confirmed: false` **не перемещаются** в `pending_vectorization` (остаются в `processing` или отдельной подочереди подтверждения).

### 4.4. Метаданные чанка (обязательные поля)

## 5. Модуль 1 — Обработка PDF (два этапа)

### 5.1. Назначение

Поэтапная обработка отсканированных PDF в **два независимых этапа** с ручным переключением серверов моделей:

| Этап | Модель | Вход | Выход |
|------|--------|------|-------|
| **Этап 1 — OCR** | Qwen3-VL OCR | `inbox/` | `pending_vectorization/` |
| **Этап 2 — Embedding** | Qwen3-Embedding | `pending_vectorization/` | `documents/` |

На каждом этапе пользователь **вручную** запускает соответствующий сервер модели, обрабатывает очередь и **останавливает** сервер перед переходом к следующему этапу. **Два сервера одновременно не работают.**

### 5.2. Общий пользовательский сценарий

1. Пользователь настраивает каталоги и параметры моделей (`localhost` или IP удалённого ПК).
2. **Этап 1:** запускает OCR-сервер → кладёт PDF в `inbox` → запускает мониторинг/очередь OCR.
3. После OCR документы с подтверждёнными метаданными попадают в `pending_vectorization/`.
4. Пользователь **останавливает** OCR-сервер.
5. **Этап 2:** запускает embedding-сервер → запускает очередь векторизации.
6. Документы из `pending_vectorization/` **поочерёдно** (один за другим) векторизуются и перемещаются в `documents/`.
7. Пользователь останавливает embedding-сервер.

### 5.3. Этап 1 — OCR (распознавание)

#### 5.3.1. Предусловия

- OCR-сервер в состоянии **«Работает»** (запущен вручную).
- Embedding-сервер **остановлен**.

#### 5.3.2. Сценарий

1. Пользователь указывает каталог `inbox` и нажимает «Запустить мониторинг OCR».
2. PDF из `inbox` → `processing` → постраничный OCR.
3. Формируются `document.md`, PDF/A, извлекаются `document_number` и `document_name`.
4. Диалог подтверждения метаданных (подтвердить / отредактировать / отложить).
5. При подтверждении: `metadata_confirmed=true`, `processing_stage=ocr_done` → перемещение в `pending_vectorization/<имя>/`.
6. Статусы в UI этапа 1: прогресс OCR, очередь `inbox` / `processing` / `pending_vectorization`.

#### 5.3.3. Pipeline этапа 1

```
PDF в inbox
    → валидация
    → перемещение в processing
    → [опционально] предобработка изображений
    → для каждой страницы: render → OCR API → document.md, text layer
    → merge → PDF/A
    → extract_metadata → metadata.json (metadata_confirmed=false)
    → [UI] диалог подтверждения номера и наименования
    → metadata_confirmed=true, processing_stage=ocr_done, vectorized=false
    → перемещение в pending_vectorization/<name>/
    → удаление из processing
```

**На этапе 1 embedding не вызывается.**

### 5.4. Этап 2 — Embedding (векторизация)

#### 5.4.1. Предусловия

- Embedding-сервер в состоянии **«Работает»** (запущен вручную).
- OCR-сервер **остановлен**.
- В `pending_vectorization/` есть документы с `metadata_confirmed=true`.

#### 5.4.2. Сценарий

1. Пользователь переключается на вкладку «Этап 2 — Векторизация».
2. Нажимает «Запустить сервер embedding» (если локальный режим).
3. Нажимает «Запустить векторизацию» — обработка очереди из `pending_vectorization/`.
4. Документы обрабатываются **строго по одному** (default: 1 документ в работе; настраиваемо, но не параллельно с OCR).
5. Для каждого документа: `chunk(document.md)` → batch embedding → `vectorstore.add` → обновление `metadata.json` (`vectorized=true`, `processing_stage=ready`).
6. Папка документа перемещается в `documents/<имя>/`.
7. Прогресс: текущий документ, N/M в очереди, число чанков.

#### 5.4.3. Pipeline этапа 2

```
Документ в pending_vectorization/<name>/
    → проверка metadata_confirmed=true
    → chunk(document.md) → embed API → vectorstore.add
    → metadata.json: vectorized=true, processing_stage=ready
    → перемещение в documents/<name>/
    → удаление из pending_vectorization/
    → следующий документ в очереди
```

**На этапе 2 OCR не вызывается.**

### 5.5. Извлечение номера и наименования документа

После OCR и формирования `document.md` модуль 1 автоматически определяет:

| Поле | Источники извлечения (приоритет сверху вниз) |
|------|-----------------------------------------------|
| `document_number` | Штамп/реквизит «№», «Исх. №», «Вх. №» на первой странице; паттерны датированных номеров; метаданные PDF (если есть) |
| `document_name` | Заголовок H1/H2 на первой странице; строка «Тема:» / «Наименование:»; имя исходного PDF (fallback) |

- Алгоритм: эвристики + опциональный запрос к OCR-модели с узким промптом «извлеки номер и наименование» (настройка `metadata.extract_via_llm`, по умолчанию Вкл).
- При неудачном извлечении поля заполняются плейсхолдерами (`—`) — пользователь обязан ввести значения в диалоге подтверждения.
- До подтверждения документ **не перемещается** в `pending_vectorization` (статус `pending_metadata` в `processing`).

## 6. Модуль 2 — Управление RAG-архитектурой

### 6.1. Назначение

Администрирование векторной базы, метаданных, файловой структуры документов; пере-embedding; синхронизация файловой системы и векторного индекса.

### 6.2. Функциональные требования

#### 6.2.1. Просмотр и редактирование метаданных

- Таблица документов: **номер документа**, **наименование документа**, имя папки, путь, число чанков, дата индексации, модель embedding, **статус подтверждения метаданных**.
- Редактирование полей метаданных документа и отдельных чанков (через форму).
- **Подтверждение метаданных:** для документов со статусом `pending_metadata` (в `processing` или `pending_vectorization`) — форма с полями «Номер документа» и «Наименование документа»; после подтверждения — при необходимости перемещение в `pending_vectorization/` (если OCR уже выполнен) или ожидание этапа 2.
- Массовое редактирование тегов (опциональное поле `tags[]` в метаданных).

#### 6.2.2. Пере-embedding (re-embed)

- Выбор документов или всей коллекции.
- Параметры: новая модель (если сменился endpoint), размер чанка, overlap.
- Прогресс: документ / чанк / ETA.
- Атомарность: при сбое — откат к предыдущей версии индекса документа (snapshot).

#### 6.2.3. Файловая структура документов

- Древовидный проводник по `pending_vectorization/` и `documents/` с операциями:
  - переименование папки/файла → обновление путей в метаданных и vectorstore;
  - удаление документа → удаление чанков из БД;
  - добавление внешнего MD/PDF → опциональная индексация без OCR.
- **Синхронизация:** кнопка «Проверить целостность» — сравнение registry.json, ФС и vectorstore; отчёт об осиротевших векторах и отсутствующих файлах.

#### 6.2.4. Управление коллекциями RAG

- Создание/удаление коллекций (для разных проектов).
- Экспорт/импорт метаданных (JSON).
- Статистика: общее число векторов, размер на диске, средняя длина чанка.

### 6.3. UI модуля 2

- Вкладка «Документы» — таблица + детали.
- Вкладка «Очередь векторизации» — документы в `pending_vectorization/`, статус embedding.
- Вкладка «Чанки» — просмотр текста чанка, соседние чанки (для документов в `documents/`).
- Вкладка «Файлы» — TreeView с контекстным меню.
- Вкладка «Синхронизация» — отчёты, кнопки исправления.
- Вкладка «Настройки RAG» — chunking, embedding API, путь к vectorstore.
- Индикатор **Embedding API**.

### 6.4. Настройки модуля 2 (с tooltips)

| Элемент | Tooltip |
|---------|---------|
| Путь к vectorstore | Локальная папка ChromaDB/Qdrant. Не перемещайте во время индексации. Влияет на все модули поиска. |

## 7. Модуль 3 — Поисковый модуль (семантический поиск)

### 7.1. Назначение

Основной рабочий интерфейс **семантического поиска** по архиву документов **без LLM-агента**. Пользователь вводит поисковый запрос; модуль векторизует запрос, выполняет поиск по RAG-базе и отображает результаты в **табличном виде**: один запрос — одна таблица результатов.

### 7.2. Подключения (настройки модуля)

| Ресурс | Настройка |
|--------|-----------|
| Каталог документов | Путь к `documents/` |
| Векторная БД | Путь / имя коллекции |
| Embedding API | Для векторизации запроса (Qwen3-Embedding-8B) |

**Search LLM не используется** — в конфигурации модуля 3 отсутствуют параметры chat/completions и streaming.

### 7.3. Сценарий поиска

```
Запрос пользователя (строка поиска)
    → embedding(query) через HTTP API
    → vectorstore.search(top_k, filters: metadata_confirmed=true)
    → для каждого результата:
          document_number, document_name — из метаданных документа
          summary — краткая вырезка текста чанка (фрагмент совпадения)
          materials — гиперссылка: имя файла document.pdf (PDF/A)
    → сортировка строк по убыванию релевантности (score)
    → отображение в таблице результатов
```

Один поисковый запрос формирует **ровно одну таблицу**. При новом запросе предыдущая таблица заменяется (опционально: история запросов в боковой панели).

### 7.4. Структура таблицы результатов

| Колонка | Источник данных | Описание |
|---------|-----------------|----------|
| **№ п/п** | Порядковый номер строки | 1, 2, 3… (не путать с номером документа) |
| **Номер документа** | `metadata.document_number` | Извлечён при обработке PDF, подтверждён пользователем |
| **Наименование документа** | `metadata.document_name` | Извлечено при обработке, подтверждено пользователем |
| **Краткое содержание ответа** | Текст чанка (`chunk_text`) | Вырезка фрагмента документа, по которому найдено семантическое совпадение с запросом; длина настраивается (`search.snippet_max_chars`, default 300 символов), с многоточием при обрезке |
| **Материалы** | `file_path` → `document.pdf` | Гиперссылка с отображаемым текстом = **имя файла PDF/A** (например, `document.pdf`); клик открывает PDF в системном просмотрщике на странице `page_start` (если поддерживается) |
| **Релевантность** | Score поиска | Опциональная колонка (скрываемая): числовое значение косинусной близости |

**Сортировка строк:** по убыванию релевантности (score). Пользователь может дополнительно сортировать по клику на заголовок колонки (номер, наименование).

**Дедупликация:** если несколько чанков одного документа попали в top-K — отображается **одна строка на документ** с наиболее релевантным чанком (настройка `search.dedupe_by_document`, default Вкл).

```

│  [●] Embedding API                              [⚙ Настройки поиска] │
├────────────────────────────────────────────────────────────────────────┤
│  [ Строка поиска........................................ ] [ Найти ]  │
├────────────────────────────────────────────────────────────────────────┤
│  Запрос: «условия поставки оборудования»          Найдено: 12          │
├──────────┬─────────────────────────┬──────────────────────┬──────────┤
│ Номер    │ Наименование документа  │ Краткое содержание   │ Материалы│
│ документа│                         │ ответа               │          │
├──────────┼─────────────────────────┼──────────────────────┼──────────┤
│ 12/34-24 │ Договор поставки...     │ ...поставщик обязуется│document.│
│          │                         │  поставить оборуд... │ pdf      │
├──────────┼─────────────────────────┼──────────────────────┼──────────┤
│ 05/11-23 │ Акт приёма-передачи     │ ...оборудование принято│document.│
│          │                         │  в соответствии...   │ pdf      │
└──────────┴─────────────────────────┴──────────────────────┴──────────┘
```

**Верхняя зона:**

- **Строка поиска** — поле ввода запроса; Enter или кнопка «Найти» запускают поиск.
- **Настройки** — кнопка/панель: `top_k`, порог релевантности, длина вырезки, фильтры по метаданным, путь к vectorstore.

**Центральная зона:**

- Таблица результатов текущего запроса (см. п. 7.4).
- Пустое состояние: подсказка «Введите запрос для поиска по архиву».
- Состояние загрузки: индикатор во время embedding и поиска.

**Дополнительно (опционально):**

- История запросов (последние N) в боковой панели — повторный клик восстанавливает запрос и таблицу.
- Экспорт таблицы результатов в CSV.

### 7.6. Настройки поиска

| Настройка | Описание | Default |
|-----------|----------|---------|
| `search.top_k` | Макс. число результатов (чанков/документов) | 20 |
| `search.score_threshold` | Мин. косинусная близость; строки ниже порога не показываются | 0.3 |
| `search.snippet_max_chars` | Макс. длина вырезки в колонке «Краткое содержание» | 300 |
| `search.snippet_highlight` | Подсветка ключевых слов запроса в вырезке | Выкл |
| `search.dedupe_by_document` | Одна строка на документ (лучший чанк) | Вкл |
| `search.only_confirmed` | Искать только в `documents/` с `vectorized=true` и `metadata_confirmed=true` | Вкл |
| `search.filters` | JSON-фильтр по метаданным (номер, теги) | — |
| `search.mmr` | MMR diversification при множестве чанков одного документа | Выкл |
| `search.hybrid` | Гибрид: вектор + BM25 по MD (опционально фаза 2) | Выкл |

Параметры `llm.*`, `stream`, `system_prompt` **исключены** из модуля 3.

### 7.7. Tooltips для модуля 3 (обязательные)

Каждый элемент управления должен иметь tooltip формата:

> **Что это:** …  
> **Зачем:** …  
> **Рекомендация:** …  
> **Влияние:** …

Пример для `search.top_k`:

> **Что это:** Максимальное число результатов в таблице после одного запроса.  
> **Зачем:** Ограничивает объём выдачи по релевантности.  
> **Рекомендация:** 20 — для обзорного поиска; уменьшите для узких запросов.  
> **Влияние:** Больше K → длиннее таблица, возможны менее релевантные строки.

Пример для колонки «Краткое содержание ответа»:

> **Что это:** Фрагмент текста документа, семантически близкий к вашему запросу.  
> **Зачем:** Позволяет оценить релевантность без открытия PDF.  
> **Рекомендация:** Увеличьте длину вырезки в настройках, если фрагмент обрывается.  
> **Влияние:** Не является сгенерированным ответом LLM — только цитата из исходного текста.

## 13. Критерии приёмки

### Модуль 1 — этап 1 (OCR)

1. OCR-сервер запускается и останавливается **вручную** из GUI; при работающем embedding-сервере запуск OCR **блокируется**.
2. PDF из `inbox` обрабатывается при включённом мониторинге и запущенном OCR-сервере.
3. После OCR и подтверждения метаданных документ находится в `pending_vectorization/`; embedding на этом этапе **не выполняется**.

### Модуль 1 — этап 2 (Embedding)

4. Embedding-сервер запускается **вручную** после остановки OCR-сервера.
5. Документы из `pending_vectorization/` векторизуются **поочерёдно** и перемещаются в `documents/`.
6. Одновременно **не работают** оба сервера моделей.

### Модуль 1 — общее

7. Итоговый файл в `documents/<имя>/` — PDF/A с поиском текста в Adobe Reader / Edge.
8. `document.md` содержит полный распознанный текст; `metadata.json` — подтверждённые номер и наименование.
9. Векторы в БД только для документов в `documents/` с `vectorized=true`.

### Модуль 2

1. Переименование папки документа обновляет пути в метаданных и vectorstore.
2. Re-embed выбранного документа завершается без потери других документов.
3. Отчёт синхронизации выявляет рассогласования ФС и БД.
4. Пользователь может подтвердить или отредактировать номер и наименование документа для записей со статусом `pending_metadata`.

### Модуль 3

1. Ввод запроса в строке поиска формирует таблицу результатов (один запрос — одна таблица).
2. Таблица содержит колонки: номер документа, наименование документа, краткое содержание (вырезка текста), материалы (гиперссылка на PDF/A).
3. Строки отсортированы по убыванию релевантности.
4. Клик по ссылке в колонке «Материалы» открывает файл `document.pdf`.
5. Документы без подтверждённых метаданных не попадают в выдачу (при `search.only_confirmed=true`).
6. Все настройки модуля имеют информативные tooltips.
7. LLM-агент **не используется** — отсутствуют элементы чата и streaming.

### Общие

1. Приложение запускается на Windows 10 и 11 без установленного Python (после сборки).
2. Размеры и позиция главного окна восстанавливаются после перезапуска.

## 14. Риски и ограничения

| Риск | Митигация |
|------|-----------|
| Qwen3-VL 30B требует мощный GPU | Локальный режим: `page_parallel=1`; поэтапность — OCR и embedding не делят VRAM одновременно |
| Нехватка VRAM при двух моделях | Взаимоисключение серверов: только одна модель в памяти |
| Нестандартный API сервера | Слой адаптеров + документация формата запроса |
| Большие PDF (500+ стр.) | Разбиение на батчи, возобновление с последней страницы |
| Качество OCR на плохих сканах | Блок предобработки, ручная повторная обработка страницы |
| PDF/A строгая валидация | Опциональная верификация через veraPDF (внешний инструмент) |

## 15. Глоссарий

| Термин | Определение |
|--------|-------------|
| **PDF/A** | Стандарт ISO для долгосрочного архивного хранения PDF |
| **OCR** | Optical Character Recognition — распознавание текста на изображении |
| **RAG** | Retrieval-Augmented Generation — в проекте: векторный поиск по чанкам документов (генерация ответа LLM не используется в модуле 3) |
| **Чанк** | Фрагмент текста фиксированного размера для векторизации |
| **Embedding** | Векторное представление текста в многомерном пространстве |
| **Вырезка (snippet)** | Краткий фрагмент текста чанка, отображаемый в результатах поиска |
| **metadata_confirmed** | Флаг подтверждения пользователем номера и наименования документа |
| **pending_vectorization** | Каталог распознанных документов, ожидающих этапа embedding |
| **ModelServerMgr** | Компонент ручного запуска/остановки локальных серверов OCR и embedding |
